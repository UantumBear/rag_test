# 공통 로거 도입

## 변경 목적

현재 프로젝트의 로깅 방식을 확인하고, 여러 모듈에서 일관되게 사용할 수 있는 공통 로거를 도입한다.

## 변경 요구사항

* 현재 프로젝트의 디렉터리 구조와 기존 로깅 사용 방식을 먼저 조사한다.
* 프로젝트 규모와 현재 구조에 가장 자연스러운 공통 로거 모듈의 위치를 판단한다.
* 공통 로거 모듈의 경로와 구조를 결정한 이유를 최종 보고에 설명한다.
* 로그 레벨, 로그 형식, 핸들러 설정은 공통 위치에서 관리한다.
* 각 기능 모듈은 공통 로거를 가져와 사용하도록 한다.
* 각 모듈에서 핸들러나 포매터를 개별적으로 중복 설정하지 않는다.
* 기존에 로깅 코드가 있다면 동작을 유지하면서 공통 로거 방식으로 정리한다.
* 처리되지 않은 예외가 발생하면 예외 정보와 스택 트레이스가 로그에 기록되도록 한다.

## 설계 원칙

* 현재 프로젝트의 구조를 우선해서 따른다.
* 공통 로거를 추가하기 위해 프로젝트 전체 구조를 변경하지 않는다.
* 로깅만을 위해 과도한 추상화나 외부 라이브러리를 도입하지 않는다.

## 문서 반영

구현과 테스트가 성공하면 다음 내용을 현재 프로젝트 명세에 반영한다.

* 공통 로거 모듈의 실제 경로
* 공통 로거의 책임
* 각 모듈에서 로거를 사용하는 방식
* 예외 로그 처리 흐름
* 해당 구조를 선택한 이유

## 완료 조건

* 공통 로거 설정 위치가 하나로 통일되어 있다.
* 기능 모듈에 중복된 핸들러와 포매터 설정이 없다.
* 주요 애플리케이션 모듈이 공통 로거를 사용한다.
* 처리되지 않은 예외의 스택 트레이스가 로그에 기록된다.
* 기존 기능과 공개 API가 유지된다.
* 관련 테스트와 전체 테스트가 모두 통과한다.
* 실제 구현 구조가 `project_spec/current/architecture.md`에 반영되어 있다.
