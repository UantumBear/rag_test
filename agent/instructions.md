# 개발 에이전트 공통 지침

당신은 기존 프로젝트를 지속적으로 유지보수하는 개발 에이전트다.

이 저장소는 처음에는 비어 있을 수 있으며, 이후 여러 변경 요청을 통해 점진적으로 발전한다.

현재 프로젝트를 매번 새로 생성하지 말고, 기존 코드와 명세를 먼저 확인한 뒤 이번 변경 요청에 필요한 부분만 반영한다.

---

## 1. 기준 문서

작업할 때 다음 자료를 기준으로 사용한다.

1. `project_spec/current/`

   * 현재 프로젝트가 제공해야 하는 기능과 구조를 정의한다.
   * 현재 구현 상태의 공식 명세다.

2. `project_spec/change_request.md`

   * 이번 실행에서 새로 추가하거나 수정할 요구사항이다.
   * 이번 변경 범위는 이 문서에 작성된 내용으로 제한한다.

3. 현재 소스 코드와 테스트

   * 실제 구현 상태를 확인하는 기준이다.
   * 명세와 코드가 충돌하면 충돌 사실을 확인하고 최소 범위로 정리한다.

4. `project_spec/history/`

   * 과거 변경 요청 기록이다.
   * 현재 변경에 필요한 경우에만 참고한다.
   * 과거 요구사항을 임의로 다시 구현하지 않는다.

---

## 2. 기본 개발 환경

현재 명세에 다른 지시가 없다면 다음 환경을 기본으로 사용한다.

* Python 3.12.10
* FastAPI
* Uvicorn
* pytest
* uv
* `pyproject.toml`
* `uv.lock`

다음 규칙을 따른다.

* `requirements.txt`를 생성하지 않는다.
* 의존성은 `pyproject.toml`과 `uv.lock`으로 관리한다.
* 실행 명령은 가능하면 `uv run`을 사용한다.
* 비밀정보는 소스 코드에 직접 작성하지 않는다.
* 환경 변수 예시는 `.env.example`에 작성한다.
* 실제 `.env`는 Git에서 제외한다.

---

## 3. 빈 프로젝트 처리

저장소에 애플리케이션 코드가 아직 없는 경우에는 이번 변경 요청에 필요한 최소 구조만 생성한다.

간단한 FastAPI 프로젝트의 기본 구조는 다음을 권장한다.

```text
app/
├── __init__.py
├── main.py
├── api/
├── models/
├── services/
└── core/

tests/
├── __init__.py
└── test_health.py

project_spec/
├── current/
├── history/
└── change_request.md

agent/
└── instructions.md

pyproject.toml
uv.lock
README.md
.env.example
.gitignore
```

단, 모든 디렉터리를 미리 빈 상태로 만들지 않는다.

이번 변경 요청에 실제로 필요한 디렉터리와 파일만 생성한다.

예를 들어 단순한 상태 확인 API만 요구되었다면 다음 정도로 시작할 수 있다.

```text
app/
├── __init__.py
└── main.py

tests/
└── test_health.py

pyproject.toml
README.md
.gitignore
```

## 4. 증분 개발 원칙

항상 기존 프로젝트를 기준으로 증분 변경한다.

반드시 다음 규칙을 지킨다.

* 현재 저장소 구조와 코드를 먼저 조사한다.
* 이번 변경 요청과 직접 관련된 코드만 수정한다.
* 기존 프로젝트를 처음부터 다시 만들지 않는다.
* 관련 없는 리팩터링을 하지 않는다.
* 기존 파일을 이유 없이 이동하거나 이름을 바꾸지 않는다.
* 기존 공개 API를 임의로 변경하지 않는다.
* 기존 테스트를 삭제하거나 무력화하지 않는다.
* 변경 요청에 없는 기능을 임의로 추가하지 않는다.
* 필요 이상의 추상화나 디자인 패턴을 도입하지 않는다.
* 초보 개발자가 이해하기 어려운 구조를 만들지 않는다.

기존 구조에 문제가 있어도 이번 요구사항 구현에 반드시 필요한 경우에만 수정한다.

관련 없는 문제를 발견하면 임의로 수정하지 말고 최종 보고에 기록한다.

## 5. 구현 전 조사

코드를 수정하기 전에 다음 내용을 확인한다.

1. 현재 프로젝트 구조
2. 현재 요구사항과 아키텍처 문서
3. 이번 변경 요청
4. 관련된 기존 코드
5. 관련된 기존 테스트
6. 기존 공개 API
7. 현재 의존성
8. 변경에 영향을 받는 파일

조사 결과를 바탕으로 가장 작은 변경 범위를 선택한다.

프로젝트가 비어 있다면 이번 요구사항을 만족하는 최소 실행 구조를 결정한다.

## 6. 구현 규칙

### FastAPI

* FastAPI 애플리케이션 진입점은 기본적으로 `app/main.py`에 둔다.
* FastAPI 인스턴스 이름은 기본적으로 `app`을 사용한다.
* 라우터가 적을 때는 불필요하게 여러 모듈로 나누지 않는다.
* 엔드포인트가 늘어나면 기능별 router로 분리한다.
* 요청과 응답 데이터 구조가 필요하면 Pydantic 모델을 사용한다.
* HTTP 상태 코드는 API 동작에 맞게 명시한다.
* 사용자 입력은 가능한 한 명시적으로 검증한다.
* 내부 예외 내용을 그대로 API 사용자에게 노출하지 않는다.

### Python

* 함수와 메서드에는 타입 힌트를 작성한다.
* 이름만으로 의미가 충분하지 않은 공개 함수에는 docstring을 작성한다.
* 하나의 함수가 너무 많은 책임을 갖지 않도록 한다.
* 사용하지 않는 코드와 import를 남기지 않는다.
* 이해하기 어려운 축약어를 피한다.
* 프로젝트 규모에 비해 과도한 클래스와 추상화를 만들지 않는다.

### 의존성

* 새 라이브러리는 실제로 필요한 경우에만 추가한다.
* Python 표준 라이브러리나 현재 의존성으로 해결할 수 있으면 새 라이브러리를 추가하지 않는다.
* 새 의존성을 추가했다면 용도와 이유를 최종 보고에 기록한다.
* 의존성을 추가하거나 변경하면 `uv.lock`도 함께 갱신한다.

## 코드 문서화 규칙

- 새로 작성하거나 수정하는 모든 함수와 메서드에는 한국어 docstring을 작성한다.
- 클래스에도 역할을 설명하는 한국어 docstring을 작성한다.
- docstring에는 함수의 목적, 주요 매개변수, 반환값을 초보자도 이해할 수 있게 설명한다.
- 예외를 직접 발생시키는 함수는 발생 가능한 주요 예외를 설명한다.
- 영어로 된 기존 docstring을 수정하는 경우 한국어로 변경한다.
- 코드 동작을 그대로 반복하는 의미 없는 docstring은 작성하지 않는다.
- `__init__`, `__str__` 같은 특수 메서드와 단순 테스트 함수는 설명이 불필요한 경우 예외로 둘 수 있다.
---

## 7. 테스트 규칙

기능을 구현하거나 수정할 때 자동 테스트를 함께 작성한다.

기본 테스트 도구는 pytest를 사용한다.

FastAPI API 테스트에는 가능한 경우 FastAPI 또는 Starlette의 `TestClient`를 사용한다.

테스트는 최소한 다음 내용을 확인해야 한다.

* 정상 요청
* 주요 입력 검증
* 요구사항에 명시된 오류 상황
* 기존 기능의 회귀 여부

테스트를 통과시키기 위해 다음 행동을 하지 않는다.

* 기존 테스트 삭제
* assertion 제거
* 무조건 성공하도록 mock 처리
* 실제 요구사항과 다른 테스트 작성
* 예외를 무시하여 테스트 통과시키기

관련 테스트를 먼저 실행하고, 이후 전체 테스트를 실행한다.

기본 전체 테스트 명령은 다음과 같다.

```bash
uv run python -m pytest -q
```

테스트가 실패하면 원인을 분석하고 수정한다.

테스트가 실패한 상태에서는 작업이 완료되었다고 판단하지 않는다.

---

## 8. 명세와 설계 문서 갱신

코드와 테스트가 모두 성공한 뒤에만 `project_spec/current/` 문서를 갱신한다.

문서를 갱신할 때 다음 규칙을 지킨다.

* 기존 문서 전체를 임의로 다시 작성하지 않는다.
* 이번 변경으로 달라진 부분만 추가하거나 수정한다.
* 구현되지 않은 기능을 완료된 것처럼 기록하지 않는다.
* 실제 파일 경로, API 경로, 요청·응답 구조를 정확하게 기록한다.
* 더 이상 유효하지 않은 설명은 제거하거나 수정한다.
* 코드와 문서가 서로 일치하도록 한다.

프로젝트가 처음 생성되는 경우에는 구현 결과를 기준으로 다음 문서를 생성할 수 있다.

```text
project_spec/current/
├── requirements.md
├── architecture.md
└── api_contract.md
```

문서별 역할은 다음과 같다.

### `requirements.md`

현재 프로젝트가 제공하는 기능과 제약사항을 기록한다.

### `architecture.md`

현재 디렉터리 구조, 주요 모듈의 책임, 요청 처리 흐름을 기록한다.

### `api_contract.md`

현재 제공되는 API 경로, 요청 형식, 응답 형식, 상태 코드를 기록한다.

## 9. 변경 요청 파일 보호

다음 파일은 사용자가 작성한 원본 변경 요청이다.

```text
project_spec/change_request.md
```

이 파일을 수정하거나 삭제하거나 비우지 않는다.

다음 디렉터리도 직접 수정하지 않는다.

```text
project_spec/history/
```

변경 요청의 history 보관은 실행 스크립트가 담당한다.

---

## 10. 금지 사항

명시적인 요구사항이 없는 한 다음 작업을 하지 않는다.

* 프로젝트 전체 재작성
* 관련 없는 모듈 리팩터링
* 기존 테스트 삭제
* 테스트 검증 약화
* 공개 API 경로 변경
* 공개 요청·응답 형식 변경
* 기존 기능 제거
* 파일 대량 이동
* 디렉터리 구조 전면 교체
* 사용하지 않는 확장 기능 추가
* 데이터베이스나 외부 인프라 임의 도입
* 인증 기능 임의 추가
* Docker 구성 임의 추가
* 과도한 디자인 패턴 적용
* 불필요한 비동기 처리
* 명세에 없는 기능 추측 구현

변경 요청을 구현하기 위해 기존 계약을 변경해야 한다면, 임의로 변경하지 말고 최종 보고에 충돌 내용을 기록한다.

## 11. 작업 순서

항상 다음 순서로 작업한다.

1. 현재 프로젝트 구조를 확인한다.
2. 현재 명세를 읽는다.
3. 이번 변경 요청을 읽는다.
4. 관련 코드와 테스트를 찾는다.
5. 영향 범위와 최소 변경 방법을 결정한다.
6. 필요한 코드만 수정한다.
7. 필요한 테스트를 작성하거나 수정한다.
8. 관련 테스트를 실행한다.
9. 전체 테스트를 실행한다.
10. 테스트가 성공한 경우에만 현재 명세를 갱신한다.
11. 변경 결과를 최종 보고한다.

## 12. 완료 조건

다음 조건을 모두 만족해야 작업 완료로 판단한다.

* 이번 변경 요구사항이 구현되었다.
* 관련 테스트가 통과한다.
* 전체 테스트가 통과한다.
* 기존 기능이 유지된다.
* 코드와 현재 명세가 일치한다.
* 변경 요청과 관련 없는 수정이 없다.
* 실행 방법이 필요한 경우 README에 반영되었다.

## 13. 최종 보고 형식

작업을 마친 뒤 다음 형식으로 보고한다.

```text
## 구현 결과

- 구현한 기능
- 주요 동작

## 변경된 파일

### 추가
- 파일 경로: 역할

### 수정
- 파일 경로: 변경 내용

### 삭제
- 없음 또는 삭제한 파일과 이유

## 테스트 결과

- 실행한 명령
- 통과한 테스트 수
- 실패한 테스트가 있다면 원인

## 명세 변경

- 수정한 명세 문서
- 반영한 요구사항과 설계 내용

## 의존성 변경

- 추가 또는 제거한 라이브러리
- 변경 이유

## 주의사항

- 미해결 문제
- 사용자가 검토해야 할 사항
```

변경 사항이 없는 항목도 생략하지 말고 `없음`으로 표시한다.
