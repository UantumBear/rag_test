# LangChain, LangGraph, LangSmith와 SaaS

이 세 이름은 같은 회사의 생태계에 속하지만 역할이 다르다.

| 이름 | 분류 | 주된 역할 | 없어도 되는 경우 |
|---|---|---|---|
| LangChain | MIT 오픈소스 프레임워크·라이브러리 | 모델과 tool을 공통 인터페이스로 연결하고 agent를 쉽게 구성 | 모델 SDK를 직접 연결할 때 |
| LangGraph | MIT 오픈소스 orchestration 프레임워크·runtime | 상태, node, edge, 중단·재개를 이용해 실행 흐름을 제어 | 단순한 단일 호출이나 고정된 짧은 chain일 때 |
| LangSmith | 관측·평가·배포 플랫폼 | trace 확인, dataset 기반 평가, 운영 중 모니터링, agent 배포 | 자체 관측·평가·배포 체계를 쓰거나 해당 기능이 필요 없을 때 |

LangChain과 LangGraph는 설치해 애플리케이션 코드 안에서 실행하는 오픈소스다.
LangSmith는 SDK 자체는 MIT 오픈소스지만, SDK가 연결하는 LangSmith 플랫폼까지
전부 오픈소스라는 뜻은 아니다.

- [LangChain 개요](https://docs.langchain.com/oss/python/langchain/overview)
- [LangChain 라이선스](https://github.com/langchain-ai/langchain/blob/master/LICENSE)
- [LangGraph 개요](https://docs.langchain.com/oss/python/langgraph/overview)
- [LangGraph 라이선스](https://github.com/langchain-ai/langgraph/blob/main/LICENSE)
- [LangSmith SDK](https://github.com/langchain-ai/langsmith-sdk)

## 한 문장씩 이해하기

### LangChain

LLM 애플리케이션을 만들 때 모델 공급자마다 다른 호출법을 일정한 인터페이스로
다루고, 모델에 tool을 제공하며, agent loop를 구성하는 일을 돕는다. 예를 들어
`create_agent(model, tools=...)`로 “모델이 답할지, tool을 호출할지 판단하고 그
결과를 다시 모델에 전달하는” 반복 실행을 만들 수 있다.

LangChain을 사용한다고 모델이 생기는 것은 아니다. 실제 추론은 연결한 외부 API
또는 로컬 모델 서버가 담당한다.

### LangGraph

여러 단계의 실행을 **공유 state를 가진 graph**로 표현하는 저수준 orchestration
도구다.

- node: 모델 호출, 검색, 검증처럼 실제 작업을 수행하는 함수
- edge: 다음에 실행할 node를 정하는 연결
- state: node 사이에서 전달되고 갱신되는 데이터
- checkpointer: 실행 상태를 저장하여 같은 thread를 이어가게 하는 장치
- interrupt: 사람의 승인이나 추가 입력을 기다리며 실행을 중단하는 기능

LangChain의 고수준 agent는 내부적으로 LangGraph를 사용한다. 하지만 LangGraph는
LangChain 없이도 직접 사용할 수 있다. 분기, 반복, 실패 후 재시도, 사람의 승인,
장시간 실행의 중단·재개를 직접 통제해야 할 때 LangGraph를 사용하는 이유가
분명해진다.

### LangSmith

LLM 애플리케이션이 **무슨 입력을 받아 어떤 모델과 tool을 거쳐 어떤 결과를
냈는지** 추적하고 평가하는 플랫폼이다. 주요 기능은 다음과 같다.

- observability: 한 요청의 실행 단계, 지연 시간, 오류와 metadata를 trace로 확인
- evaluation: dataset과 evaluator를 이용해 버전별 결과를 비교
- monitoring: 운영 중 품질과 오류를 관찰
- deployment: LangGraph 기반 agent의 배포와 실행을 관리

LangChain이나 LangGraph를 실행하기 위해 LangSmith가 필수인 것은 아니다.
LangSmith를 연결하면 실행 자체보다 **관찰·평가·운영**을 돕는 기능이 추가된다.

- [LangSmith 평가](https://docs.langchain.com/langsmith/evaluation)
- [LangChain 제품 구성](https://docs.langchain.com/oss/python/concepts/products)

## 세 도구의 관계

```text
사용자 요청
    ↓
애플리케이션
    ├─ LangChain: 모델·tool·agent를 편리하게 구성
    │      └─ LangChain agent의 실행 기반은 LangGraph
    ├─ LangGraph: state와 node/edge로 실행 흐름을 제어
    └─ LangSmith SDK: 실행 trace와 평가 결과를 전송
                ↓
          LangSmith 플랫폼
```

따라서 셋은 서로 대체하는 제품이 아니다. LangChain만 쓸 수도 있고, LangGraph를
직접 쓸 수도 있으며, 어느 쪽이든 LangSmith를 연결하거나 연결하지 않을 수 있다.

## SaaS란?

SaaS(Software as a Service)는 사용자가 서버와 소프트웨어 전체를 직접 설치·운영하는
대신, 공급자가 운영하는 소프트웨어를 네트워크를 통해 사용하는 제공 방식이다.
보통 계정, API key 또는 웹 UI로 접근하며 공급자가 업데이트와 기반 인프라를
관리한다.

다만 “LangSmith는 SaaS다”라고만 말하면 불완전하다. 공식 문서상 LangSmith에는
다음 배포 형태가 있다.

| 형태 | 운영 위치와 책임 |
|---|---|
| Cloud | LangChain이 관리하는 완전 관리형 서비스 |
| Hybrid | control plane은 LangChain, data plane은 고객 환경 |
| Self-hosted | 전체 stack을 고객 환경에 배포·운영 |

Hybrid와 Self-hosted는 Enterprise 요금제 대상이다. 개발·테스트를 위한 로컬 Agent
Server와 전체 LangSmith 플랫폼의 self-hosting도 서로 다른 개념이므로 구분해야
한다.

- [LangSmith 배포 형태](https://docs.langchain.com/langsmith/platform-setup)
- [Self-hosted LangSmith](https://docs.langchain.com/langsmith/self-hosted)

## “SaaS를 감싸는 API”란?

일반적으로 **wrapper API** 또는 **facade API**를 만들었다는 뜻이다. 다음과 같은
구조를 생각할 수 있다.

```text
업무 애플리케이션
       ↓ 회사가 정의한 요청 형식
wrapper API
  - 인증·권한 확인
  - 입력 검증과 정책 적용
  - 공급자별 요청 형식으로 변환
  - 응답·오류 형식 통일
       ↓
외부 SaaS API 또는 self-hosted 제품 API
```

장점은 각 애플리케이션이 공급자의 API key와 세부 형식을 직접 알 필요가 없고,
공통 정책과 기록 방식을 한곳에 둘 수 있다는 것이다. 그러나 wrapper를 만들었다고
원래 SaaS가 오픈소스가 되거나 로컬 제품으로 바뀌는 것은 아니다. 실제 데이터가
어디로 전송되고 어디에 저장되는지, 어떤 라이선스가 적용되는지는 wrapper 뒤의
대상과 배포 형태를 따로 확인해야 한다.

## Facade란?

`facade`는 건물의 정면이라는 뜻이며, 소프트웨어에서는 **내부의 복잡한 구성요소를
감추고 클라이언트에 더 단순하고 일관된 진입점을 제공하는 설계 방식**을 뜻한다.
클라이언트는 뒤에 몇 개의 서비스가 있는지와 각 서비스의 호출 순서를 모두 알지
않아도 facade가 제공하는 인터페이스만 사용한다.

```text
facade가 없을 때
클라이언트 ─┬→ 인증 서비스
             ├→ 모델 서비스
             └→ 기록 서비스

facade가 있을 때
클라이언트 → facade API → 인증·모델·기록 서비스
```

예를 들어 클라이언트가 `POST /ask` 하나만 호출하면 facade가 내부에서 인증을
확인하고, 검색과 모델 호출을 실행하고, 결과를 정해진 형식으로 반환할 수 있다.
이 경우 `/ask`가 단순한 진입점이고, 내부 호출 순서와 제품별 API 형식은 facade
뒤에 숨겨진다.

### Wrapper와 Facade의 차이

두 용어는 현장에서 엄격히 구분하지 않고 함께 쓰기도 하지만 강조점은 다르다.

| 용어 | 강조점 |
|---|---|
| wrapper | 특정 객체나 API를 한 겹 감싸 호출 형식을 바꾸거나 기능을 덧붙임 |
| facade | 하나 이상의 복잡한 하위 시스템 앞에 단순하고 통합된 인터페이스를 제공 |

공급자 API 하나를 거의 그대로 감싸 인증이나 오류 형식만 추가했다면 wrapper라는
표현이 자연스럽다. 여러 API와 처리 단계를 묶어 업무 애플리케이션에 하나의 단순한
API로 제공한다면 facade의 성격이 더 강하다. 하나의 구현이 두 역할을 동시에 할
수도 있다.

Facade는 내부 구현에 대한 의존성을 줄이는 장점이 있지만, 다음 사실까지 보장하지는
않는다.

- 외부 SaaS 호출이나 네트워크 의존성이 사라지는 것은 아니다.
- 하위 시스템의 장애가 자동으로 해결되는 것은 아니다.
- 공급자 교체가 항상 쉬워지는 것은 아니다. 공급자 고유 기능이 facade의 계약에
  노출되어 있으면 여전히 결합될 수 있다.
- facade에 인증, 변환, 재시도 등 너무 많은 책임을 모으면 새로운 병목이나 단일
  장애 지점이 될 수 있다.

Microsoft의 API Gateway 설명도 gateway를 여러 서비스에 대한 단일 진입점이자
분산 시스템에 적용된 Facade와 유사한 패턴으로 설명한다.

- [Microsoft Learn: API Gateway pattern](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/architect-microservice-container-applications/direct-client-to-microservice-communication-versus-the-api-gateway-pattern)

# 1. 4-GPU 토폴로지, NVLink와 PCIe 병목

## 1.1 NVLink와 PCIe의 역할

PCIe는 CPU, GPU, NIC 등의 장치를 연결하는 범용 인터페이스다. NVLink는 NVIDIA가
GPU 간 고대역폭·저지연 통신을 위해 제공하는 인터커넥트다. NVIDIA는 NVLink를
전통적인 PCIe 기반 연결보다 빠른 GPU 간 연결로 설명한다.

- [NVIDIA NVLink 개요](https://www.nvidia.com/en-us/products/workstations/nvlink-bridges/)
- [CUDA 다중 GPU 프로그래밍 가이드](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/multi-gpu-systems.html)

다중 GPU에서 모델을 tensor parallelism으로 나누면 GPU들이 계산 중간 결과를
반복적으로 교환해야 한다. 이때 통신량이 많은 GPU들이 느린 링크를 사이에 두고 있으면
통신이 전체 처리 시간의 병목이 될 수 있다. NVIDIA의 성능 가이드도 통신 그룹이 서로
다른 고속 연결 도메인에 걸치면 더 느린 링크가 병목이 될 수 있다고 설명한다.

### 여기서 말하는 link란?

link는 두 장치 사이에서 데이터를 전달하는 **개별 연결 통로**다. 도로에 비유하면
GPU와 GPU 사이에 놓인 한 개의 차선과 비슷하다.

`NVLink`라는 이름에는 기술 전체를 가리키는 `NVLink`와, 그 기술로 만든 개별 연결을
가리키는 `NVLink link`라는 두 가지 쓰임이 있다. GPU 한 쌍이 여러 NVLink link로
연결될 수 있으며, 사용 가능한 총 GPU 간 bandwidth는 GPU 세대, 연결된 link 수,
통신 방향과 topology에 따라 달라진다.

PCIe에서도 `lane`은 직렬 데이터 전송의 기본 통로이고, 여러 lane을 묶어 `x4`, `x8`,
`x16`처럼 표시한다. 따라서 다음 용어는 구분해야 한다.

```text
link       두 장치를 잇는 연결
lane       PCIe link를 구성하는 기본 전송 통로
bandwidth  해당 연결이 단위 시간에 전달할 수 있는 데이터 양
topology   여러 GPU·CPU·switch가 어떤 경로로 연결됐는지를 나타낸 구조
```

두 GPU 사이에 물리적인 경로가 있다는 사실만으로 NVLink를 사용한다고 단정할 수 없다.
실제 경로가 NVLink인지 PCIe인지, peer-to-peer 접근이 가능한지는 GPU 모델과 서버
topology 및 설정을 확인해야 한다.

- [NVIDIA DCGM의 NVLink/PCIe bandwidth 정의](https://docs.nvidia.com/datacenter/dcgm/2.4/user-guide/feature-overview.html)

- [NVIDIA Megatron Bridge 성능 가이드](https://docs.nvidia.com/nemo/megatron-bridge/latest/performance-guide.html)

## 1.2 “2장 + 2장 NVLink” 구성에서 확인할 점

GPU 네 장이 다음처럼 연결됐다고 가정한다.

```text
GPU 0 ═══ GPU 1       GPU 2 ═══ GPU 3
       NVLink pair           NVLink pair

GPU 1 ───── PCIe/CPU/PCIe switch ───── GPU 2
```

각 쌍 내부 통신은 NVLink를 사용할 수 있지만, 두 쌍 사이의 통신 경로는 실제 서버
토폴로지에 따라 PCIe switch 또는 CPU root complex를 통과할 수 있다. 따라서
tensor-parallel group을 네 GPU 전체로 잡으면 일부 collective communication이
더 느린 경로를 사용할 가능성이 있다.

그러나 다음 문장은 현재 정보만으로 사실이라고 할 수 없다.

> “NVLink가 중간에서 끊겨 397B 모델 성능이 정확히 n% 감소한다.”

모델 성능은 다음 조건에 따라 달라진다.

- GPU 정확한 모델과 GPU 메모리
- PCIe 세대와 lane 수
- NVLink 세대와 실제 링크 수
- CPU 및 PCIe switch 토폴로지
- 모델 정밀도(BF16, FP8, INT4 등)
- tensor/data/expert/pipeline parallelism 구성
- 입력 길이, 출력 길이, batch size와 동시 요청 수
- 사용하는 inference engine과 collective library

따라서 이 수치는 해당 서버에서 동일한 workload로 측정해야 한다.

## 1.3 토폴로지와 링크를 확인하는 방법

```bash
nvidia-smi topo -m
nvidia-smi nvlink --status
```

`nvidia-smi topo -m` 결과에서 GPU 쌍 사이의 연결 종류를 확인한다. 단, 토폴로지
표만으로 실제 애플리케이션 성능을 알 수는 없다. NVIDIA의 `nvbandwidth`는 GPU 간
메모리 전송 bandwidth와 latency를 측정하기 위한 도구다.

- [NVIDIA nvbandwidth 설명](https://developer.nvidia.com/blog/nvidia-nvbandwidth-your-essential-tool-for-measuring-gpu-interconnect-and-memory-performance/)

모델 성능은 별도로 같은 조건에서 측정해야 한다.

```text
고정해야 할 값
├── 모델과 quantization
├── tensor/expert parallel 설정
├── 입력·출력 토큰 길이
├── 동시 사용자 수
└── inference engine 버전

비교할 값
├── request throughput
├── output token throughput
├── TTFT
├── inter-token latency
└── p50/p95/p99 end-to-end latency
```

## 1.4 Qwen3.5-397B-A17B의 숫자 의미

`Qwen3.5-397B-A17B`는 Mixture-of-Experts(MoE) 모델이다.

- `397B`: 전체 parameter 규모
- `A17B`: 토큰 처리 시 활성화되는 parameter 규모가 약 17B라는 모델명 표기

공식 Hugging Face 저장소의 모델 파일 전체 표시는 약 807GB다. 활성 parameter가
17B라는 사실이 “17B 모델만큼의 GPU 메모리만 필요하다”는 뜻은 아니다. 추론 시
선택되는 expert는 일부여도 전체 weight를 저장하거나 계층적으로 배치해야 하기 때문이다.

- [Qwen3.5-397B-A17B 공식 모델 저장소](https://huggingface.co/Qwen/Qwen3.5-397B-A17B/tree/main)
- [Qwen 공식 GitHub 릴리스 정보](https://github.com/QwenLM/Qwen3.5)

parameter 값만 이용한 순수 weight 크기의 이론적 근사치는 다음과 같다.

```text
BF16/FP16: 397B × 2 bytes   ≈ 794 GB
FP8/INT8: 397B × 1 byte    ≈ 397 GB
4-bit:     397B × 0.5 byte ≈ 198.5 GB
```

실제 필요 메모리는 이보다 단순하지 않다. quantization metadata, KV cache, activation,
workspace, communication buffer 및 runtime overhead가 추가된다. 따라서 위 계산은
“모델이 이 GPU 구성에 들어가는가”를 확정하는 계산이 아니라 weight 규모의 하한을
감 잡기 위한 근사치다.

### KV cache란?

Transformer의 attention은 입력으로부터 Query(`Q`), Key(`K`), Value(`V`)를 계산한다.
자기회귀 언어 모델은 다음 token을 하나 생성할 때마다 이전 token 전체를 참고한다.
cache가 없다면 이미 처리한 이전 token들의 `K`와 `V`를 생성 단계마다 다시 계산해야
한다.

KV cache는 각 attention layer에서 이전 token들의 Key와 Value tensor를 저장해 두었다가
다음 token 생성에 재사용하는 메모리 영역이다.

```text
첫 token 생성
  이전 문맥의 K·V 계산 → KV cache에 저장

다음 token 생성
  저장된 K·V 재사용 + 새 token의 K·V만 추가
```

이 방식은 중복 계산을 줄여 generation을 빠르게 하지만 메모리를 사용한다. 일반적인
dynamic cache는 처리한 sequence가 길어질수록 커진다. 동시에 처리하는 sequence 수,
문맥 길이, model layer와 KV head 구성, cache 자료형 등이 KV cache 크기에 영향을
준다. 따라서 긴 context와 높은 동시성에서는 model weight가 GPU에 들어간 뒤 남은
메모리가 충분하더라도 KV cache 때문에 처리 가능한 요청 수가 제한될 수 있다.

KV cache는 model weight와 다르다.

- model weight: 학습으로 정해진 model parameter이며 요청 간 공유된다.
- KV cache: 각 요청의 처리된 token 문맥에서 만들어지며 요청 진행에 따라 변한다.

- [Hugging Face KV cache 원리](https://huggingface.co/docs/transformers/main/cache_explanation)
- [Hugging Face cache 전략](https://huggingface.co/docs/transformers/kv_cache)

### Runtime overhead란?

runtime overhead는 이 문맥에서 **model weight 파일 크기 외에 실제 추론 프로그램을
실행하기 위해 추가로 소비되는 자원**을 묶어 부르는 표현이다. 하나의 고정된 메모리
항목이나 일정한 비율을 뜻하지 않는다.

GPU 메모리 관점에서는 다음이 포함될 수 있다.

- 연산 도중 만들어지는 activation과 temporary tensor
- CUDA/PyTorch가 관리하거나 재사용을 위해 예약한 memory
- CUDA Graph 또는 kernel 실행을 위한 buffer와 workspace
- 다중 GPU collective communication에 사용하는 NCCL buffer
- inference engine 자체의 자료구조와 실행 중 임시 할당

KV cache와 quantization metadata도 model의 순수 parameter byte 계산 외에 필요한
메모리지만, 용도와 크기를 따로 측정할 수 있으므로 보통 capacity 계획에서는
`weight`, `KV cache`, `activation peak`, `runtime/allocator/communication`처럼 나누어
기록하는 편이 원인 파악에 유리하다.

예를 들어 vLLM의 memory profiling 구현은 model weight, PyTorch activation peak,
non-PyTorch memory를 구분하고 남은 공간을 KV cache에 할당한다. PyTorch는 실제
tensor가 점유한 `memory_allocated`와 caching allocator가 관리하는
`memory_reserved`도 구분한다.

따라서 “weight가 GPU 메모리보다 작으니 실행된다”라고 판단하면 안 된다. 동일 model도
batch, sequence length, parallelism, inference engine 설정에 따라 peak memory가
달라질 수 있으므로 실제 serving 조건에서 측정해야 한다.

- [vLLM worker memory profiling](https://docs.vllm.ai/en/v0.10.2/api/vllm/worker/worker.html)
- [PyTorch CUDA memory 관리](https://docs.pytorch.org/docs/main/notes/cuda.html#memory-management)
- [NCCL communication buffer 설정](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2234/user-guide/docs/env.html#nccl-buffsize)

## 1.5 70B 모델 검토 시 정확히 비교할 것

`nvidia/llama-3.1-nemotron-70b-instruct`는 실제 존재하는 NVIDIA 모델이다.

397B MoE 모델을 70B dense 모델로 바꾸면 weight 규모와 배포 조건이 달라진다. 하지만
parameter 수만 보고 품질이나 속도의 우열을 확정할 수 없다. 실제 업무 prompt와

- 정답률 또는 task 성공률
- tool-call 정확도
- TTFT와 inter-token latency
- output tokens/s와 requests/s
- GPU memory 사용량
- 동시 요청 증가에 따른 p95 latency
- 요청당 비용


### TTFT란?

TTFT(Time To First Token)는 요청 처리 후 **첫 번째 output token이 나올 때까지 걸린
시간**이다. 사용자는 전체 답변이 완성되기 전이라도 첫 token이 도착하면 응답이
시작됐다고 느끼므로 streaming 서비스의 초기 응답성을 나타내는 지표로 사용한다.

다만 측정 시작점은 도구마다 확인해야 한다.

- 사용자 관점의 end-to-end TTFT는 요청 전송부터 첫 token 수신까지 측정할 수 있다.
- vLLM의 현재 per-request `time_to_first_token_ms`는 request가 scheduled된 시점부터
  첫 output token 생성까지이며, queue time은 별도 metric이다.

따라서 서로 다른 시스템의 TTFT를 비교할 때 queue 포함 여부와 client/network 구간
포함 여부가 같아야 한다. 입력 prompt가 길면 첫 token 전에 수행하는 prefill 계산량도
커질 수 있다.

### Inter-token latency란?

Inter-token latency(ITL)는 첫 token 이후 **서로 이어지는 output token 사이의
시간 간격**이다. 예를 들어 token 도착 시각이 다음과 같다면:

```text
token 1: 100 ms
token 2: 120 ms
token 3: 145 ms

간격: 20 ms, 25 ms
평균 ITL: 22.5 ms
```

ITL이 짧을수록 streaming 답변이 더 빠르고 매끄럽게 출력된다. TTFT는 답변이
시작되기까지의 대기 시간을, ITL은 답변이 시작된 뒤의 생성 속도를 설명하므로 둘을
따로 측정한다.

vLLM의 `mean_itl_ms`는 첫 output token부터 마지막 output token까지의 decode 시간을
`생성 token 수 - 1`로 나눈 값이다. output token이 하나뿐이면 token 사이 간격이
없으므로 이 값은 `null`이다.

- [vLLM per-request metric 정의](https://docs.vllm.ai/en/latest/features/per_request_metrics/)

# 3. OpenCode와 SaaS 코딩 어시스턴트

## 3.1 먼저 비교 대상을 정확히 나누기

OpenCode는 open-source AI coding agent이며 terminal, desktop app, IDE extension
형태로 사용할 수 있다. 사용자는 LLM provider를 연결하거나 OpenAI-compatible
provider와 local model을 설정할 수 있다.

- [OpenCode 공식 소개](https://opencode.ai/docs/)
- [OpenCode provider 설정](https://opencode.ai/docs/providers)

“SaaS 코딩 어시스턴트”는 하나의 제품명이 아니다. GitHub Copilot, Claude Code의
서비스 계정, Codex 등의 서로 다른 제품을 한 그룹으로 묶은 일반 표현이다. 따라서
보안, 가격, 데이터 보존, 지원 모델을 비교하려면 반드시 구체적인 제품·요금제를 정해야
한다.

## 3.2 사실에 기반한 구조 차이

| 구분 | OpenCode | 특정 vendor의 SaaS 코딩 어시스턴트 |
|---|---|---|
| agent client | open-source이며 직접 실행 가능 | vendor가 제공하는 client/extension/service |
| 모델 선택 | 여러 provider 또는 local model 연결 가능 | 해당 제품이 지원하는 모델과 정책 범위 |
| 운영 책임 | provider, key, 모델, update, policy를 사용자가 선택·관리 | 상당 부분을 vendor가 관리 |
| 비용 구조 | 선택한 provider/API 또는 local inference 비용 | 제품별 구독 또는 사용량 정책 |
| 데이터 경로 | 선택한 provider와 설정에 따라 달라짐 | 해당 SaaS 제품 계약과 설정에 따라 달라짐 |
| customization | source/config/agent/tool/MCP 수준으로 가능 | 제품이 공개한 extension과 설정 범위 |

## 3.3 장단점으로 볼 수 있는 실제 trade-off

OpenCode의 장점:

- 여러 provider와 local model을 연결할 수 있다.
- agent, permission, tool, MCP 설정을 직접 관리할 수 있다.
- 특정 모델 vendor에 client가 강하게 묶이는 정도를 줄일 수 있다.

OpenCode 사용자가 부담하는 것:

- provider credential과 권한을 안전하게 관리해야 한다.
- 모델별 tool calling 호환성과 품질을 직접 평가해야 한다.
- local serving을 선택하면 GPU 운영, monitoring, update도 직접 담당한다.
- open-source client를 쓴다고 해서 요청 데이터가 자동으로 local에만 남는 것은 아니다.
  외부 API provider를 사용하면 데이터는 그 provider로 전송된다.

SaaS 제품에서 흔히 기대할 수 있는 이점:

- 설치, 인증, 모델 update 및 IDE 연동이 제품 차원에서 제공될 수 있다.
- 조직용 policy, audit, support가 요금제에 포함될 수 있다.

하지만 SaaS의 데이터 사용·보존·보안 정책은 제품과 계약마다 다르므로 “SaaS는
안전하다/안전하지 않다”처럼 일괄적으로 결론 내릴 수 없다.

## 3.4 비교 실험표

코딩 agent는 일반 대화 benchmark만으로 선택하면 안 된다. 동일 repository snapshot과
동일 task로 다음을 측정한다.

| 영역 | 측정값 |
|---|---|
| 기능 성공 | test pass rate, task success rate |
| 변경 품질 | 불필요한 diff, regression, reviewer 수정량 |
| agent 능력 | 올바른 tool 선택, tool argument 정확도, loop 발생률 |
| 성능 | 완료 시간, TTFT, output tokens/s |
| 비용 | 성공한 task당 API·GPU 비용 |
| 안전 | 승인 없는 write/command 실행 횟수, secret 노출 여부 |
| 운영 | 장애율, rate limit, 재시도 후 성공률 |

# 4. RAG 검색과 답변 품질

## 4.1 RAG는 검색과 생성을 따로 평가한다

RAG는 최소한 두 단계로 나뉜다.

```text
질문
  ↓
Retriever ── 검색 문서의 품질
  ↓
Generator ── 답변의 정확성·근거성
  ↓
답변
```

검색이 실패하면 generator는 필요한 근거를 받지 못한다. 반대로 검색이 성공해도
generator가 문서를 잘못 해석하거나 근거 없는 내용을 추가할 수 있다. 따라서 최종
답변 점수 하나만으로 원인을 찾기 어렵다. LangSmith 공식 RAG 평가 안내도 검색 관련성,
답변 정확성, 답변 관련성, groundedness를 구분한다.

- [LangSmith RAG 평가 가이드](https://docs.langchain.com/langsmith/evaluate-rag-tutorial)
- [중간 단계 평가 가이드](https://docs.langchain.com/langsmith/evaluate-on-intermediate-steps)

## 4.2 평가 데이터가 먼저다

Recall, Precision, MRR, nDCG를 계산하려면 질문마다 어떤 문서 또는 chunk가 relevant인지
판정한 ground truth가 필요하다.


문서 단위 relevant label과 chunk 단위 label은 서로 다르다. 시스템이 chunk를 반환하면
평가도 원칙적으로 chunk ID를 기준으로 해야 한다. 같은 내용을 overlap으로 나눈
중복 chunk를 어떻게 판정할지도 사전에 정의해야 한다.

## 4.3 Precision@k

상위 `k`개 검색 결과 중 relevant 결과의 비율이다.

```text
Precision@k = 상위 k개 중 relevant 결과 수 / k
```

예를 들어 상위 5개 중 relevant chunk가 3개이면 `Precision@5 = 3/5 = 0.6`이다.

Precision이 낮으면 불필요한 문서가 LLM context를 차지한다. 이것은 token 비용과
latency를 늘리고 답변에 혼선을 줄 수 있다.

## 4.4 Recall@k

질문에 대해 존재하는 전체 relevant 결과 중 상위 `k`개 안에 포함된 비율이다.

```text
Recall@k = 상위 k개에서 찾은 relevant 결과 수 / 전체 relevant 결과 수
```

전체 relevant chunk가 4개인데 상위 5개 검색 결과에서 3개를 찾았다면
`Recall@5 = 3/4 = 0.75`다.

RAG의 첫-stage retriever에서는 recall을 중요하게 보는 경우가 많다. 필요한 근거를
후보 집합에서 놓치면 뒤의 reranker나 LLM이 복구할 수 없기 때문이다. 하지만 이것은
“precision은 중요하지 않다”는 뜻이 아니다. 일반적인 설계는 넓게 후보를 가져온 뒤
reranker 또는 filter로 최종 context의 precision을 높이는 방식이다.

```text
Retriever: 상대적으로 큰 candidate_k로 recall 확보
    ↓
Reranker/filter: 순서와 precision 개선
    ↓
Generator: 작은 최종 context 사용
```

## 4.5 F1

Precision과 Recall의 조화평균이다.

```text
F1 = 2 × Precision × Recall / (Precision + Recall)
```

둘 중 하나가 낮으면 F1도 낮아진다. 단, ranked retrieval에서는 단일 F1만으로 결과
순서의 좋고 나쁨을 충분히 표현하지 못한다.

## 4.6 Reciprocal Rank와 MRR

Reciprocal Rank는 첫 번째 relevant 결과의 순위 역수다.

```text
첫 relevant 결과가 1위: RR = 1
첫 relevant 결과가 2위: RR = 1/2
첫 relevant 결과가 5위: RR = 1/5
```

MRR(Mean Reciprocal Rank)은 여러 질문의 RR 평균이다. 첫 번째 정답 근거를 빨리
보여주는 것이 중요한 검색에서 유용하다. 여러 relevant 문서를 모두 얼마나 잘 찾았는지는
충분히 표현하지 않는다.

## 4.7 nDCG@k

nDCG는 relevance를 단순한 0/1이 아니라 `매우 관련 있음`, `부분적으로 관련 있음`처럼
등급으로 평가할 수 있고, relevant 결과가 상위에 있을수록 더 높은 점수를 준다.
이상적인 순서의 DCG로 정규화하므로 일반적으로 0에서 1 사이 값을 갖는다.

OpenSearch Search Relevance Workbench는 `Precision@k`, `MAP@k`, `nDCG@k` 등을
지원하며 nDCG를 실제 순위와 이상적인 순위를 비교하는 지표로 설명한다.

- [OpenSearch 검색 품질 평가](https://docs.opensearch.org/latest/search-plugins/search-relevance/evaluate-search-quality/)

## 4.8 “Recall 목표를 SOTA 기준으로 잡는다”가 성립하지 않는 이유

모든 RAG에 통용되는 단일 SOTA Recall 목표치는 없다. 점수는 다음에 종속된다.

- 평가 dataset과 질문 난이도
- corpus와 chunking 방식
- relevant 판정 기준
- `k` 값
- dense, sparse, hybrid 검색 방식
- embedding 및 reranker
- 문서 언어와 domain

예를 들어 `Recall@5`와 `Recall@100`은 같은 지표가 아니다. 다른 공개 benchmark의
점수를 사내 PDF RAG의 목표로 바로 복사할 수도 없다.

권장 순서는 다음과 같다.

1. 실제 사용 질문과 실패 사례로 평가 set을 만든다.
2. 현재 시스템의 baseline을 측정한다.
3. 업무상 허용 가능한 누락률과 latency budget을 정한다.
4. 같은 dataset과 같은 `k`에서 변경 전후를 비교한다.
5. retrieval과 answer 품질을 별도로 regression test한다.

## 4.9 검색 품질을 높이는 실험 순서

다음은 검증 가능한 실험 항목이지, 항상 성능이 오른다는 보장은 아니다.

1. PDF parsing 및 metadata 정확성 검사
2. chunk size와 overlap 실험
3. BM25 baseline 구축
4. dense vector baseline 구축
5. hybrid retrieval 비교
6. metadata filter 적용
7. candidate 수 증가 후 reranking
8. 중복 결과 제거 또는 MMR 비교
9. 질문 rewrite 비교

OpenSearch의 MMR은 relevance와 결과 간 다양성을 함께 고려하여 중복 결과를 줄이기
위한 기능이다.

- [OpenSearch MMR 문서](https://docs.opensearch.org/latest/vector-search/specialized-operations/vector-search-mmr/)

# 5. Harness, rule-based 평가, model 평가, HITL과 metadata

## 5.1 Agent harness란 무엇인가

Agent harness는 모델 하나를 가리키는 말이 아니다. 모델이 실제 작업을 반복 수행할 수
있도록 둘러싼 실행 구조를 뜻한다.

```text
Agent harness
├── model 호출
├── system prompt
├── tool registry와 실행
├── state와 memory
├── middleware
├── permission과 sandbox
├── retry와 stop condition
├── HITL
└── trace, metric, evaluation
```

같은 모델이라도 harness의 tool 설명, context 구성, retry 정책 및 permission이 다르면
task 성공률과 비용이 달라질 수 있다. 따라서 “모델 성능”과 “agent system 성능”을
분리해서 평가한다.

## 5.2 Rule-based 평가

코드로 명확히 판정할 수 있는 항목은 deterministic rule로 평가한다.

- JSON schema validation
- 필수 citation 존재
- 금지된 tool 호출 여부
- tool argument schema 일치
- unit/integration test 통과
- latency 또는 token budget 초과
- 검색 결과에 gold chunk ID 포함

장점은 반복 실행해도 판정 기준이 일정하고 저렴하다는 것이다. 단점은 rule로 표현하지
않은 의미적 오류를 잡지 못한다는 것이다.

## 5.3 Model-based 평가

정답의 의미적 동등성, 답변의 근거성, 요약의 충실도처럼 단순 문자열 비교가 어려운
항목은 LLM-as-judge를 사용할 수 있다. 그러나 judge도 모델이므로 비결정성과 bias가
있을 수 있다. 다음 장치를 함께 둔다.

- 구체적인 rubric
- reference answer 또는 evidence
- structured output
- judge model과 version 기록
- 사람이 검토한 calibration set
- 중요한 항목은 rule-based check와 결합

LangSmith는 RAG 평가에서 correctness, relevance, groundedness와 retrieval relevance를
서로 다른 비교 대상으로 구분한다.

- [LangSmith 평가 개념](https://docs.langchain.com/langsmith/evaluation-concepts)

## 5.4 Human-in-the-loop(HITL)

HITL은 agent 실행 중 인간이 승인, 수정 또는 거절하도록 제어권을 넘기는 패턴이다.
LangChain의 `HumanInTheLoopMiddleware`는 정책에 지정된 tool call 전에 실행을
중단하고 다음 결정을 받을 수 있다.

- `approve`: 그대로 실행
- `edit`: argument를 수정해 실행
- `reject`: 실행하지 않고 feedback 반환

상태를 중단 후 재개하려면 checkpointer와 동일한 thread ID가 필요하다.

- [LangChain HITL 문서](https://docs.langchain.com/oss/python/langchain/human-in-the-loop)
- [LangGraph interrupt 문서](https://docs.langchain.com/oss/python/langgraph/interrupts)

HITL을 적용할 대표 후보:

- 파일 삭제 또는 대규모 변경
- 외부 메시지 발송
- 결제·환불
- production DB write
- 개인정보가 포함된 외부 API 호출

모든 tool을 승인 대상으로 만들면 처리 시간이 늘고 사용자가 무의식적으로 승인하는
문제가 생길 수 있다. 위험도에 따라 `allow`, `review`, `deny` 정책을 구분해야 한다.

## 5.5 Metadata 정의

metadata는 trace와 실행을 검색·분류·비교하기 위한 구조화된 key-value다.

권장 예:

```json
{
  "environment": "staging",
  "app_version": "rag-v3",
  "prompt_version": "answer-v5",
  "retriever_version": "hybrid-v2",
  "embedding_model": "model-id",
  "reranker_model": "model-id",
  "top_k": 20,
  "final_k": 5,
  "user_segment": "internal",
  "dataset_version": "gold-2026-07-28"
}
```

비교 실험에서 model 이름만 기록하고 prompt, dataset, retrieval 설정을 기록하지 않으면
어떤 변경이 점수 차이를 만들었는지 재현할 수 없다. LangSmith는 trace에 arbitrary
metadata와 tag를 추가하고 이를 filtering/grouping에 사용할 수 있다.

- [LangSmith metadata와 tag](https://docs.langchain.com/langsmith/add-metadata-tags)

개인정보, secret, 전체 문서 본문은 metadata에 넣지 않는다. metadata는 관측과 실험
구분용 식별자 및 설정값 중심으로 설계한다.

# 6. 성능 bottleneck과 RPS/TPS

## 6.1 RPS와 TPS는 같지 않다

### RPS(Requests Per Second)

서버가 1초 동안 완료하거나 처리한 요청 수다.

```text
RPS = 완료 요청 수 / 측정 시간(초)
```

### Token throughput

1초 동안 처리한 token 수다. 보통 다음을 분리한다.

- input/prompt tokens per second
- output/generation tokens per second

요청마다 입력·출력 길이가 다르므로 RPS가 같아도 token throughput은 다를 수 있다.
반대로 batching을 통해 token throughput이 증가해도 개별 사용자의 latency가 좋아진다는
보장은 없다.

vLLM은 running/waiting request 수, prompt/generation token counter, TTFT,
inter-token latency, end-to-end latency를 서로 다른 metric으로 노출한다.

- [vLLM metrics 설계](https://docs.vllm.ai/en/stable/design/metrics/)

## 6.2 사용자 경험과 서버 처리량 지표

| 지표 | 뜻 |
|---|---|
| Queue time | scheduler에서 실행을 기다린 시간 |
| TTFT | 처리 시작부터 첫 output token까지의 시간 |
| ITL | 연속 output token 사이의 평균 지연 |
| Generation time | 첫 token부터 마지막 token까지 decode 시간 |
| E2E latency | 요청부터 전체 응답 완료까지의 시간 |
| Output tokens/s | 일정 시간에 생성한 output token 수 |
| RPS | 일정 시간에 처리한 요청 수 |

vLLM의 per-request `tokens_per_second`는 scheduling부터 마지막 output token까지의
구간으로 계산되므로 decode 속도만의 역수가 아니다.

- [vLLM per-request metric 정의](https://docs.vllm.ai/en/latest/features/per_request_metrics/)

## 6.3 병목을 찾는 순서

```text
1. workload 고정
   - input/output 길이 분포
   - 동시 사용자 수
   - streaming 여부

2. end-to-end 분해
   - queue
   - retrieval
   - rerank
   - prompt build
   - LLM prefill/decode
   - network

3. resource 관측
   - GPU utilization/memory
   - KV-cache 사용률
   - CPU/RAM
   - PCIe/NVLink traffic
   - OpenSearch latency

4. 변경은 한 번에 하나
   - batch/concurrency
   - parallelism
   - quantization
   - candidate_k/final_k

5. p50뿐 아니라 p95/p99 확인
```

평균만 보면 일부 사용자의 긴 대기 시간을 숨길 수 있다. 운영 목표는 예를 들어
“특정 workload에서 p95 TTFT와 p95 E2E latency를 만족하면서 최소 RPS를 달성한다”처럼
latency와 throughput을 함께 정의해야 한다.

# 7. LangChain `create_agent()`와 middleware

## 7.1 `create_agent()`

LangChain의 `create_agent()`는 model과 tools를 받아 tool-calling loop를 실행하는
graph-based agent runtime을 만든다. 내부적으로 LangGraph를 사용한다.

- [LangChain Agent 공식 문서](https://docs.langchain.com/oss/python/langchain/agents)

```python
from langchain.agents import create_agent

agent = create_agent(
    model=model,
    tools=[search_documents],
    system_prompt="검색 근거만 사용해 답하세요.",
)
```

단순한 agent를 시작할 때 표준 진입점으로 사용할 수 있다. 직접 `StateGraph`를 만드는
것이 항상 더 좋은 것은 아니다. custom branching, 병렬 fan-out, 명시적인 deterministic
step처럼 기본 agent loop를 넘어서는 orchestration이 필요할 때 LangGraph를 직접
구성한다.

## 7.2 Middleware

middleware는 agent loop의 특정 지점에서 요청·응답·tool 실행을 가로채 동작을 추가한다.

대표 사용:

- dynamic prompt
- tool filtering
- tool error handling
- retry
- call limit
- HITL
- planning/todo
- summarization
- logging과 policy

middleware로 횡단 관심사를 분리하면 모든 tool과 node에 같은 코드를 반복하지 않아도
된다.

## 7.3 정확한 명칭: `TodoListMiddleware`

`ToolListMiddleware`가 아니라 `TodoListMiddleware`다. 이 middleware는 agent가
구조화된 todo list를 작성·관리하도록 `write_todos` tool과 관련 state를 추가한다.

- [TodoListMiddleware API reference](https://reference.langchain.com/python/langchain/agents/middleware/todo)

```python
from langchain.agents import create_agent
from langchain.agents.middleware import TodoListMiddleware

agent = create_agent(
    model=model,
    tools=tools,
    middleware=[TodoListMiddleware()],
)
```

Todo list가 모델의 추론 능력을 자동으로 높이는 것은 아니다. 여러 단계 작업에서 현재
계획과 진행 상태를 명시적으로 관리하기 위한 harness 기능이다.

## 7.4 `OmitFromInput`

`OmitFromInput`은 state field를 agent의 외부 입력 schema에서는 제외하기 위한 type
annotation이다. 해당 값이 state에 존재할 수 없다는 뜻이 아니라, 호출자가 최초 입력으로
제공해야 하는 field가 아니라는 뜻이다.

- [LangChain middleware type reference](https://reference.langchain.com/python/langchain/agents/middleware/types)

공식 `PlanningState`의 `todos`가 대표 예다.

```python
from typing import Annotated, NotRequired
from langchain.agents import AgentState
from langchain.agents.middleware.types import OmitFromInput


class PlanningState(AgentState):
    todos: Annotated[NotRequired[list[dict]], OmitFromInput]
```

`todos`는 middleware가 내부에서 생성·갱신할 값이므로 사용자가 매 호출 입력에 넣도록
요구하지 않는다.

`OmitFromInput`을 “모델 prompt에서 반드시 숨긴다” 또는 “checkpoint에 저장하지 않는다”로
해석하면 안 된다. 입력 schema에서 제외하는 annotation이다. 출력까지 제외하려면
`OmitFromOutput`, middleware 내부 전용 state라면 `PrivateStateAttr` 같은 별도 의미를
검토해야 한다.

# 8. LangGraph State와 Human-in-the-loop

## 8.1 State

LangGraph의 graph는 여러 node가 공유하는 state를 읽고 update하면서 진행한다.
node는 state를 입력받고 state update를 반환하는 Python 함수다.

- [LangGraph Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)

```python
from typing import TypedDict


class RAGState(TypedDict, total=False):
    question: str
    documents: list[str]
    answer: str
```

여기서 state는 전역 변수와 다르다. graph 실행의 데이터 계약이며, reducer,
checkpointing, persistence와 함께 사용할 수 있다.

RAG 예:

```text
START
  ↓
retrieve: question → documents
  ↓
generate: question + documents → answer
  ↓
END
```

## 8.2 State와 persistence는 같은 말이 아니다

state를 정의했다고 실행 사이에 자동으로 영구 보존되는 것은 아니다. 실행을 중단·재개하거나
여러 turn의 상태를 보존하려면 checkpointer를 설정하고 thread ID로 실행을 식별해야 한다.

- [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

## 8.3 `interrupt()`

`interrupt()`는 graph node 실행을 중단하고 외부 입력을 기다린다. 재개할 때는 같은
thread ID와 `Command(resume=...)`를 사용한다.

```python
from langgraph.types import interrupt


def approval_node(state):
    approved = interrupt(
        {
            "action": "delete_index",
            "index": state["index_name"],
        }
    )
    return {"approved": approved}
```

주의할 사실:

- checkpointer가 필요하다.
- interrupt payload는 JSON-serializable 값이어야 한다.
- resume 시 interrupt가 있던 node는 처음부터 다시 실행된다.
- interrupt 이전 side effect는 재실행되어도 안전하도록 idempotent하게 설계해야 한다.

- [LangGraph interrupt 규칙](https://docs.langchain.com/oss/python/langgraph/interrupts)

# 9. Subagent 구현 패턴

공식 LangChain multi-agent 문서는 subagents, handoffs, router를 서로 다른 pattern으로
구분한다. 이름이 비슷하지만 제어권과 state 흐름이 다르다.

- [LangChain Multi-agent 개요](https://docs.langchain.com/oss/python/langchain/multi-agent/index)

## 9.1 Agent as tool(Subagents)

중앙 main agent가 subagent를 tool처럼 호출한다.

```text
사용자
  ↓
Main/Supervisor Agent
  ├── search_agent tool
  ├── coding_agent tool
  └── review_agent tool
```

특징:

- main agent가 대화를 유지한다.
- main agent가 어떤 subagent를 호출할지 결정한다.
- subagent 결과는 main agent로 돌아온다.
- subagent context를 main context와 격리할 수 있다.
- 독립 작업이면 여러 subagent를 병렬 호출할 수 있다.

- [LangChain Subagents 문서](https://docs.langchain.com/oss/python/langchain/multi-agent/subagents)

간단한 형태:

```python
from langchain.agents import create_agent
from langchain.tools import tool

research_agent = create_agent(model=model, tools=[web_search])


@tool
def research(query: str) -> str:
    """주제를 조사하고 근거를 반환한다."""
    result = research_agent.invoke(
        {"messages": [{"role": "user", "content": query}]}
    )
    return result["messages"][-1].content


main_agent = create_agent(model=model, tools=[research])
```

적합한 경우:

- 전문 domain이 구분된다.
- subagent가 사용자와 직접 장기 대화할 필요가 없다.
- main agent가 결과를 종합해야 한다.

agent 두 개가 필요하지 않은 단순 작업에 subagent를 추가하면 LLM 호출, latency,
비용과 실패 지점만 늘어난다.

## 9.2 Handoff

handoff는 state 변화로 현재 행동 또는 active agent의 제어권을 전환하는 pattern이다.

```text
사용자 ↔ 접수 Agent
             ↓ handoff
사용자 ↔ 전문 Agent
```

특징:

- state에 `current_step` 또는 `active_agent` 같은 값을 둔다.
- tool call이 state를 갱신하여 전환을 일으킬 수 있다.
- 전환된 상태/agent가 사용자와 직접 대화할 수 있다.
- 여러 turn에 걸친 순차 workflow에 적합하다.

- [LangChain Handoffs 문서](https://docs.langchain.com/oss/python/langchain/multi-agent/handoffs)

적합한 경우:

- 본인 확인 후에만 환불 단계로 이동
- 접수 agent에서 전문 상담 agent로 대화 제어권 이전
- 요구사항 수집 → 검토 → 승인처럼 순서가 중요한 과정

handoff 시 LLM이 만든 tool call에는 대응하는 `ToolMessage`가 있어야 한다. 이 pairing이
없으면 message history가 올바르지 않을 수 있다.

## 9.3 Router

router는 입력을 분류하여 하나 이상의 전문 agent 또는 workflow로 보낸다.

```text
질문
  ↓
Router
  ├── 인사 질문 → HR Agent
  ├── 카드 질문 → Card RAG
  └── 기술 질문 → Tech Agent
```

특징:

- 분류가 핵심 단계다.
- 하나의 대상에 보내거나 여러 대상을 병렬 호출할 수 있다.
- 결과를 별도 synthesis 단계에서 합칠 수 있다.
- stateless router는 요청별로 독립적으로 동작한다.

- [LangChain Router 문서](https://docs.langchain.com/oss/python/langchain/multi-agent/router)

## 9.4 세 패턴 선택 기준

| 질문 | 적합한 패턴 |
|---|---|
| main agent가 전문가를 필요할 때 호출하는가? | Agent as tool / Subagents |
| 사용자와 대화하는 주체가 단계에 따라 바뀌는가? | Handoff |
| 입력 category가 분명하고 먼저 분류하면 되는가? | Router |
| 순서와 분기가 완전히 명시적인가? | Custom LangGraph workflow |

패턴을 섞을 수도 있다. 예를 들어 router가 domain을 선택한 뒤, 선택된 main agent가
subagent를 tool로 호출할 수 있다. 다만 먼저 단일 agent와 tool만으로 해결 가능한지
확인하는 것이 좋다.

# 10. 이 내용을 실제로 공부하는 순서

## 1단계: 현재 RAG를 평가 가능하게 만들기

- 질문 20~50개 작성
- 질문마다 gold chunk와 reference answer 기록
- `Precision@k`, `Recall@k`, `MRR`, `nDCG@k` 구현
- 검색과 최종 답변 평가 분리

## 2단계: 검색 실험

- BM25, vector, hybrid baseline 비교
- chunk size와 `k` 변경
- metadata filter와 reranker 비교
- 모든 실험에 dataset/config version 기록

## 3단계: 성능 실험

- input/output 길이와 concurrency 고정
- RPS, input/output tokens/s 구분
- TTFT, ITL, E2E p50/p95/p99 측정
- GPU topology와 communication traffic 확인

## 4단계: Agent 기본기

- `create_agent()`와 tool 한 개
- middleware로 logging과 tool error 처리
- `TodoListMiddleware`
- custom state와 `OmitFromInput`
- 위험한 tool에 HITL 적용

## 5단계: Multi-agent

- 먼저 agent-as-tool 한 개
- router와 비교
- multi-turn 제어권 이전이 필요할 때만 handoff
- 단일 agent baseline보다 실제 성공률이 좋아지는지 평가

# 11. 확인이 필요한 미해결 항목

다음은 공개 정보만으로 확정할 수 없어 원래 메모의 작성자 또는 미팅 참석자에게
확인해야 한다.

1. 네 장의 GPU 정확한 모델, 메모리, PCIe/NVLink topology
2. “30% 감소”를 측정한 benchmark 조건과 원본 결과
3. 코딩 어시스턴트 비교 대상 SaaS 제품과 요금제
4. RAG에서 relevant로 판정할 단위(document/page/chunk)
5. Recall을 우선한다는 업무상 이유와 허용할 precision·latency 범위
6. 목표 workload의 입력/출력 길이와 동시 사용자 수

이 정보가 없을 때 특정 모델이 더 빠르다거나, 30% 느리다거나, 목표 Recall이 몇
퍼센트여야 한다고 단정하면 사실 문서가 아니라 가정 문서가 된다.
